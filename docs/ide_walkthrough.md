# F-IDE, example programs, and representations

Paths in this guide are relative to the repository root unless stated otherwise. Start with the supplied PC example and its matching default factory model.

## Start the IDE

From the release root:

```sh
cd F_IDE_Project
python main.py
```

The window has **Open**, **Save**, and **Compile & Build** buttons, a source editor, and a compiler-message panel. **Open** accepts `.falang` and legacy `.fl` files. **Save** saves the editor text; compiling uses the current editor contents, including unsaved edits.

For a first demonstration, select `examples/pc_mms_order_demo.falang` in the Open dialog. Click **Compile & Build**, inspect the messages, then choose a destination for the COE file. Cancelling the COE save dialog leaves the other generated outputs available. Rebuilds replace the graph and FB files in the working directory, so copy an output elsewhere if you want to keep a particular version.

## What the PC example manufactures

The example represents one customized PC order on a modular manufacturing system. Resource declarations describe assembly, inspection, packaging, and recovery capabilities; `Warehouse` provides storage.

| FaLang task | Production content | What to inspect |
|---|---|---|
| `AssemblePC` | Load material; assemble motherboard, CPU, memory, storage, GPU, cooling, power supply, and case | Component/model parameters; sequential material versions; material-shortage catch and adjustment steps |
| `TestAndPackage` | Power-on, benchmark, and thermal tests; accessory check; packaging; storage | Inspection operations; machine-failure catch and quality-rework compensation |
| `Main` | Call the two tasks and pass the resulting material between them | Task calls are inlined into the CFG; material dependencies connect the stages |

The source selects MB_2, CPU_3, RAM_2, SSD_1, GPU_2, and COOLING_1. These are order choices; physical allocations come from the compiler and target model. The GUI build generates static outputs. It does not run the discrete-event factory simulation or inject faults.

## Open the CFG and other compiler outputs

With the documented launch command, the following files appear directly in `F_IDE_Project/`:

| Output | Meaning and how to view it |
|---|---|
| `factory_ssa_cfg.html` + `factory_ssa_cfg.svg` | Open the HTML in a browser, keeping the SVG beside it. This is the SSA CFG before phi elimination and physical allocation. Hover source-navigation items or CFG blocks to inspect their mapping. Open the SVG directly to zoom further. |
| `factory_ssa_cfg.dot` | Graphviz source for the same CFG; inspect in a text editor or render with Graphviz. |
| `factory_mdg.dot` / `.svg` | Manufacturing dependencies before register allocation; open the SVG in a browser. |
| `factory_mdg_post_ra.dot` / `.svg` | Dependencies after allocation and post-allocation scheduling, including physical transfer constraints; open the SVG in a browser. |
| `factory_fb_config.json` | Function Block instances, parameters, and connections; open in a JSON/text editor. |
| `factory_fb_config.xml` | IEC 61499-style network export for inspection or downstream tooling. |
| The chosen `.coe` file | FISA instruction words for memory initialization; inspect in a text editor. Its save location is selected separately. |

On Windows, after the build, run these commands from a second terminal in the release root:

```powershell
Start-Process '.\F_IDE_Project\factory_ssa_cfg.html'
Start-Process '.\F_IDE_Project\factory_mdg_post_ra.svg'
```

In the CFG, follow the normal path from entry to exit, then inspect the catch/compensate branches. SSA suffixes identify successive material states. The CFG is control flow; the MDG adds manufacturing dependencies. Neither is an animated execution trace.

## Inspect the residual representation

The research compiling path (`compile_order_program`) and `WorksetComposer` provide the order and residual representations used by the studies. They are separate from the GUI's FISA/COE build. From the release root:

```sh
python scripts/demo_representations.py
```

The command prints the full path to a new `results/demo_<timestamp>/index.html`. Open that file in a browser. No web server is required. The directory contains:

| File | Use |
|---|---|
| `index.html` | Order choices, operation states before/after supplied progress, material versions, fixed locations, annotated instructions, and the full order CFG |
| `order.falang` | Actual program generated by the case-study PC order generator; open in F-IDE to inspect its task and response definitions |
| `representations.json` | The same data in machine-readable form, including the initial RGC allocation and both workset snapshots |
| `order_cfg.dot`, `order_cfg.svg` | Full order CFG after SSA conversion, phi elimination, and target lowering; SVG is optional and requires Graphviz |
| `compiler.log` | Messages from the research compiling path and any Graphviz rendering diagnostics |

The default seed is 9. It generates a basic-grade PC with no optional GPU and with cooling. Compared with the manually written introductory example, its rules select a different configuration and one power-on test. Its generated response definitions also differ; inspect the source to see the rule-driven program used by the case-study compiler.

The default snapshot marks three operations complete (inbound load, base assembly, CPU installation) and the next one (memory installation) running. The page uses these terms from the implementation:

| State | Interpretation |
|---|---|
| `frozen` | Completed work, excluded from new allocation |
| `carried` | Running work; known material locations are retained |
| `pending` | Work requiring allocation in the residual workset |
| `handler` | Inactive exception-response instructions; excluded from the normal allocation workset |

Expand **Inspect annotated CFG instructions** to inspect instruction-level states and operation keys. Compiler-inserted transfers and structural/control instructions have no production-operation key and remain pending. In JSON, `initial_rgc_allocation` records the initial allocation; `progress.pinned_locations` records the carried material locations retained from it. Sequence numbers are zero-based.

This command compiles a real order and uses the real workset composer with **supplied progress**. It does not infer progress from a simulation, trigger HUR/CBC, or rerun allocation after the snapshot. The full CFG remains visible for context; the state tables show its residual interpretation. Use the [case-study runner](reproduction.md) for simulated execution and policy comparisons.

For another snapshot, run:

```sh
python scripts/demo_representations.py --seed 9 --completed 6 --out results/pc_after_six
```

`--completed` is a count, not a sequence ID. The next operation is marked running if one remains. `--out` must name a new subdirectory of `results/`; existing directories are rejected. `--no-graph` skips SVG rendering while retaining the HTML tables, DOT, and JSON. To compare snapshots, use the same seed and distinct output directories.

## Other examples and models

| Example | Intended use | Model guidance |
|---|---|---|
| `examples/pc_mms_order_demo.falang` | Recommended end-to-end GUI demonstration of PC assembly, testing, and packaging | Uses the default `core/factory_target_model.json` |
| Generated `results/demo_*/order.falang` | Inspect rule-based order generation and residual states | Uses the same default PC model in the demo exporter |
| `examples/task_call_demo.falang` | Small CNC task-definition/call and material-return syntax example | Requires a model with matching CNC resources and operation descriptions |
| `examples/full_syntax_demo.falang` | Explore branches, loops, task calls, and exception syntax | Requires matching CNC/AOI/loader capabilities and action definitions |
| `examples/motherboard_minimal/motherboard_example.falang` | Minimal motherboard program/model pair | Accompanied by `minimal_target_model.json`; intended for explicit model selection through `CompilerProxy(target_model_path=...)` |

The GUI currently loads the default model and has no model-selection control. Do not expect every syntax example to compile against that PC model. For another domain, use its designated model through the Python API or the case-study runner.

## Troubleshooting

- **Tkinter cannot import or no window opens:** run `python -m tkinter` to check the Python/Tcl/Tk installation and desktop availability.
- **Graphviz is missing:** install the Graphviz application, add its `bin` directory to `PATH`, reopen the terminal, and check `dot -V`. Recompile after fixing it. DOT may be present even when SVG/HTML export fails.
- **Graphs show an earlier program:** check the latest compiler messages. A failed build or failed export may leave files from a previous run; verify their modification times.
- **An operation or capability is rejected:** check that the example and target model match. Start with the PC example before trying the separate syntax demonstrations.
- **No residual output appears after a GUI build:** run `scripts/demo_representations.py` from the release root; the GUI build does not export residual worksets.
